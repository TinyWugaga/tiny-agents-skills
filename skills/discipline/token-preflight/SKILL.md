# token-preflight

本 skill 是獨立(standalone)skill,分別部署於 Claude、Codex、ChatGPT 等平台,不掛在任何
plugin 或 namespace 之下。不論在哪個平台呼叫,skill 本身的 runtime canonical name 都固定為
裸名稱 `token-preflight`,不會、也不應該出現 `xxx:token-preflight`、`xxx/token-preflight`
這類 namespace 前綴形式。

回覆語言依當前對話的全域 Instructions 設定,本 skill 不另行規定或覆蓋。

## 與更高優先權指示的關係

本 skill 的分級、報告與停損建議,不得覆蓋或放寬使用者、系統或專案層級的更高優先權指示
(例如使用者的明確指示、安全與資料保護限制、平台既有規則)。與更高優先權指示衝突時,以
更高優先權指示為準,本 skill 只在其允許的範圍內運作。

## 目標

在動手前把任務的成本量級講清楚,給使用者一次踩剎車或改走便宜路線的機會;執行途中若成本
依可量測 baseline 明顯超出預估,也要停下來讓使用者重新決定。

**本 skill 只因 token 成本觸發,不作為需求歧義的確認理由。**
需求不清楚該不該問,由 `judgment` skill 負責,不要在 pre-flight 報告裡夾帶需求澄清問題。

## 成本 proxy

分級只看以下三個可量測的數字,不臆測其他因素:

- **檔案數**:預期要讀或要動的檔案數量
- **工具呼叫數**:預期需要的工具呼叫次數
- **行數**:預期產出的程式碼或文字行數

三者任一達到「強訊號」門檻,或兩個以上達到「弱訊號」門檻,就進 pre-flight。

## 第一步:分級

收到任務後,依下表分級。**只有「大」需要走 pre-flight**,「小」和「中」直接執行,不要提及
本 skill。

| 等級 | 特徵                                     | 行動            |
| ---- | ---------------------------------------- | --------------- |
| 小   | 單一問題、小段程式碼、0-2 次工具呼叫     | 直接執行        |
| 中   | 讀 1-2 個明確指定的檔案、產出 100-500 行 | 直接執行        |
| 大   | 一個強訊號,或兩個以上弱訊號              | 執行 pre-flight |

### 強訊號(單一即攔)

- 未指明範圍的 codebase 讀取(「看一下我的專案」「掃過整個 repo」)
- 大範圍變更詞涵蓋多個模組:「重寫」「重構全部」「每一個都改」
- 預期工具呼叫數 ≥ 10(研究型任務、多輪搜尋、多步驟自動化)
- 預期產出橫跨 ≥ 5 個檔案

### 弱訊號(需同時滿足兩個以上才攔)

- 預期檔案數 ≥ 3,或需讀一整個目錄
- 預期行數 > 500
- 預期工具呼叫數落在 5-9
- 任務結構要求多輪迭代(生成 → 驗證 → 修正的迴圈)

## 第二步:Pre-flight 報告格式

暫停執行,輸出以下三段,整份不超過 10 行:

**規模與成本結構**:大。一兩句話說明最貴的環節是什麼、為什麼,並附上觸發本判斷的成本
proxy 數字(檔案數 / 工具呼叫數 / 行數,擇一至二)。這組數字就是後續中止點要比對的
baseline。

**更便宜的替代路線**(最多 2 條,只列真正可行的):

- 先列變更清單確認,再逐項執行
- 只輸出 diff 或摘要
- 先做一個小樣本驗證方向,對了再擴大
- 拆成階段,每階段結束可停

**建議**:明確說出推薦哪條路與理由。

然後停下來等回覆。使用者說「直接做」就照原需求執行,不再重複提醒。

## 第三步:執行中的中止點

Pre-flight 只在起點判斷,但成本失控通常發生在途中。中止點的判斷方式依有沒有 baseline
分兩種:

### 有 baseline(走過 pre-flight,報告裡已寫出成本 proxy 預估)

對照第二步報告裡寫下的數字:

- 實際工具呼叫次數達到預估的兩倍時,停下來
- 實際檔案數或行數比預估多一個量級(例如預估 3 個檔案,發現要讀 20 個),停下來

### 無 baseline(任務原判「小」或「中」,沒走 pre-flight,沒有預估數字可比)

不要事後編一個數字湊比較。改為監看「第一步」的強訊號清單:途中新出現任一項強訊號(工具
呼叫累積到 10 次以上、要動的檔案累積到 5 個以上、範圍變成「重寫全部」),就停下來,依當下
實際規模重新判級——當成一個新的分級判斷,不是回頭套用不存在的 baseline。

重試無進展該不該停,由 `judgment` skill 判斷,本 skill 不重複處理。

停下來的格式是一句話現況 + 一句話選項:
「已經跑了 N 次工具呼叫,發現還需要讀 X 才能完成,要繼續還是縮範圍到 Y?」
不要輸出完整報告,不要重跑分級。

## 規則

- 寧可漏攔中型任務,不要誤攔小任務——頻繁攔截比多花 token 更傷體驗。
- 報告必須具體。「提供更多資訊可以降低成本」這種空話禁止出現。
- 只能給量級判斷(小/中/大)與成本 proxy 數字(檔案數/工具呼叫數/行數的預估),不要編造
  精確的 token 數字。只有執行環境能可靠顯示 token budget 或已用量時,才可以回報實際數字。
- 「放行不再攔」只適用於同一個任務內、成本邊界相近的後續階段(例如同一批次的下一個檔案、
  同一次重構的下一個模組),且僅限已經完整走過一次 pre-flight 並被使用者放行之後。換成另一
  個新任務,即使類型相同,也要重新走一次分級——不能用「同類任務」當理由跳過。
- 使用者明確表示趕時間或不在乎成本時,跳過 pre-flight 與中止點。
