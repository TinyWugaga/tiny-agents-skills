# tiny mode

補 `~/.claude/CLAUDE.md` 沒寫到的慣例。兩邊衝突時以 CLAUDE.md 和專案的 AGENTS.md 為準。

## 驗收

- 驗收條件逐條標 PASS、FAIL 或 👤（要使用者實機才能判），每條附證據：檔案:行號、量測數字或截圖路徑。「已照指令修改」這類執行說明不算證據。
- 新的量測指標先跑對照組。故意做一個應該被抓到的改動，確認指標量得出差異，之後才拿它判通過。量不出差異的指標，結果一律不採信。
- 視覺改動在同尺寸下截改前、改後兩張圖比對，預設桌機 1440×900、手機 390×844。WebGL 頁面要等內建瀏覽器面板顯示後再截，面板隱藏時 rAF 會停，canvas 不會初始化。
- 你碰不到的環境，例如實體手機或使用者桌機 Chrome 的 on-device AI，不要請使用者描述現象。先做量測工具，例如匯出 JSON 的 bench 頁或 `window.__xxx.lastRun` 除錯物件，請使用者跑完貼回，再依數字判斷。
- 獨立驗收只驗不修。驗收契約寫定後就不改；量尺本身有錯時，照契約判，另外登記「量尺誤報」，由使用者決定是否修契約。
- 驗收條件之間互相衝突時，不自己取捨。回報裡另開「需要你決定」一段，列出選項和各自的代價。

## 外部 review 與執行回報

- 沒有外部 AI 時，ADR、spec、計畫照這個順序審：
  1. 作者列出決策依賴的假設，以及每個假設的推翻條件。寫好後就不改，審查照條文判。
  2. 開新 session 或 subagent 審。只給決策文件和推翻條件，不給對話紀錄、作者的理由或 STATUS 檔。
  3. 審查題目用反方問法：「假設半年後這個決策失敗，最可能的三個原因是什麼」，加上「寫出最強的替代方案，說明它在哪個情境下勝過原案」。每條附證據或驗證方式。
  4. 可以觀察的假設（效能、API 行為、版面、做不做得到）用 spike 或量測決定，不靠審查意見。
  5. 平台事實（API 行為、額度、版本）查官方來源並附查閱日期，因為同模型的審查者會帶著同樣的記憶錯誤。
  6. 剩下的產品取捨用 `grill-me` 交給使用者決定。
- 使用者貼來 ChatGPT 或 Codex 的 review，逐條判成立、部分成立或不成立，附證據，再只修使用者指定的項目。review 檔在 `docs/reviews/` 時，修完在原檔勾選已處理的項目。
- 使用者貼來「驗收以下執行結果」，代表你是指揮者，執行的是另一個 session 或 AI。照上一輪指令的驗收條件逐條核，再寫下一輪指令，每輪指令都附可量測的驗收條件。

## 前端與設計

- 使用者給的 hex 陣列是主題色票，做成 design token。參考圖只取風格，不搬圖裡的元素或物件。
- 提方案時用 A／B 或「路線 1／2」標記，分段的方案標「第一段」「第二段」，讓使用者能用「走 A」「照 B 第一段」回覆。每段做完停下等確認再進下一段。
- 可行性不明的功能先做 spike：dev 模式的除錯按鈕或最小原型，量出 availability、耗時、輸出品質，結論寫進 `docs/`。轉成正式功能前先出方案。
- Figma 作品集：設計系統（Theme、Palette、元件庫）在 Figma 原生建立，畫面從本機網頁匯入成可編輯圖層。
- Artifact 專案的改動先在本機累積，使用者說「發布」才 republish，回報時列出這次發布包含的改動。

## Git

- 只在使用者說時 commit。一輪做完，在結尾說明可以 commit 的範圍。commit message 寫明驗證狀態，例如「eval 未跑」「只做 diff 與 read-back」。
- push、merge PR、刪分支都等使用者下令。刪除前先列出要刪的 local branch、remote branch 和 worktree，使用者確認清單後才刪。
- 部署指令（`npm run deploy`、寫入 `~/.codex` 等）交給使用者自己跑，你只給指令和預期結果。
- 不是 git repo 的專案（例如 Blender 檔），每次修改前存編號快照：`<name>_vNN_pre-<step>.<ext>`。

## Skill 與 harness

- skill 改在 `~/Documents/Agents/tiny-agents-skills` 的 `develop`，依該 repo 的 AGENTS.md。不改 `~/.agents/skills/` 底下的安裝副本。
- 要花錢的 eval（付費 session、API 呼叫）先估成本，等使用者給金額上限和 subject model 再跑。沒有放行時只跑零成本的測試。

## Handoff

使用者常在 session 結束時要「下一個 session 的 handoff 摘要」。照這個順序寫：

1. 專案路徑、主檔、執行環境（Node 版本、背景執行指令）。
2. 先讀：要讀的文件和段落。
3. 目前狀態：已通過和未通過的項目，未通過的附數字和量測檔路徑。
4. 已定案：方向調整和理由。
5. 下一段要做的事：步驟、驗收條件、工具呼叫上限。
6. 開工前要存的快照或 branch。

一段工作有工具呼叫上限時，回報實際用量和事前估計的差距。
