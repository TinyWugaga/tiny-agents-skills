# 派工調度守則

主對話預設自己做。派工是手段,不是義務。本 skill 只回答「要不要派、派給誰、怎麼寫派工單、
失敗了怎麼調整能力」;完成判斷與驗收判準一律不在這裡。

平台能力的具體數值(model 別名、effort 級別、fast mode 計費、巢狀深度、內建 agent 的模型與
工具範圍)都會過期,一律查 [`references/claude-code-capabilities.md`](references/claude-code-capabilities.md),
不憑記憶引用。

**要動手寫派工 prompt 時,先讀 [`references/templates.md`](references/templates.md)**:依任務類型選對
模板,把佔位逐一填實,不要憑印象自己重寫一份格式相近的派工單。模板裡已經寫死的約束與回報格式
是該類任務的驗收下限,**填模板時一併帶出,不得因為自己寫的派工單看起來已經夠完整就省略**。
例如重構類走模板 3,它對不變量、既有測試與測試結果的要求都要留在派工單裡。

## 何時派工

只在三種情況派 subagent:

| 情境 | 派給 | 理由 |
|---|---|---|
| 使用者明確要求派工 | 依任務性質選 agent | 尊重指令 |
| 需要 fresh context 的對抗性驗證(驗收、第二意見) | 唯讀 agent(見「驗證交棒」) | 驗證不自驗 |
| 大範圍純機械掃描,只要清單、不需理解(>10 檔或全 repo 搜尋) | 唯讀 agent,並**明寫低成本 model** | 省額度,結論可機械核對 |

其餘情況(讀大 diff、讀多檔、查網頁、批次改檔)自己做,用 plan mode 與分段讀取控制範圍。

**判準:派工 prompt 寫起來比自己讀還費事,就自己做。**

**成本可以否決,但不得靜默否決。** 落入上表情境仍判斷不划算時(一次 `grep` 就能解決、
範圍小到自己讀更快),可以自己做,但**必須在回應裡講出否決的理由與依據**;
同時告知使用者仍可要求派工;
使用者聽完仍要求派工,就照做,不再爭論。

- ✅ 「全 repo 找出所有呼叫 `dispatch()` 且 event type 為 `consumed` 的位置」→ 全 repo 搜尋,
  落入第三種情境,派工。
- ❌ 「讀這兩個檔案然後改一行」→ 不落入任何一種情境,且派工單比自己做還長,自己做。

**巢狀深度是本機政策,不是平台事實**:平台預設允許 subagent 再派 subagent(深度見 capabilities
參照)。本機以環境變數限制為一層,所以**需要多階段時由主對話依序派工、在主對話整合**,
不要指望工人自己找幫手。改這個限制屬於需使用者核准的變更。

## 派工三件套(缺一不發)

每個派工 prompt 必含:

1. **目標與動機**:做什麼、為什麼做。動機讓 agent 在規格沒寫到的地方做出正確取捨。
2. **驗收條件**:可機械檢查的清單。「寫好測試」不合格;「`npm test` 全綠且新增
   `freshness.test.ts` 覆蓋過期/臨期/新鮮三個分支」合格。
3. **回報格式**:規定回什麼、不回什麼(見「回報合約」)。

另外必附:**agent 需要的一切上下文都寫進 prompt**(檔案路徑、先前決策、錯誤訊息)。
subagent 看不到主對話歷史,「如前所述」對它是空字串。部分內建 agent 連 CLAUDE.md 與 git
status 都不會載入(見 capabilities 參照),**專案規則要給檔案路徑,不能假設它知道**。

**任何一件套填不出來,代表還沒想清楚,先想清楚再派。**

## 回報合約

subagent 的回報只准包含:

- 結論(做了什麼 / 找到什麼 / 判定通過與否)
- 證據指標:`檔案路徑:行號`、指令與結果摘要
- 遇到的阻礙與未完成項(如有)

**禁止**:貼整段程式碼、貼完整 diff、貼搜尋到的原文。長產物一律落檔,回報只傳路徑。
主對話收到超過 ~40 行的回報且非明確要求時,視為違約,下次派工時在 prompt 中重申本節。

計數與統計一律機械來源(指令輸出),不用心算;清單筆數與機械計數不符時逐筆解釋差異,
不准直接報一個數。

## 升降級路徑

| 情況 | 動作 |
|---|---|
| 派給低成本 model 的子任務**錯一次** | 不重試,直接自己做或升一階 |
| 自己第一輪失敗 | 先查明實際輸入、依賴與錯誤來源再試第二輪。單次失敗是資訊不足,不是能力不足 |
| 同一子任務**連錯兩次** | 升 effort 一階,並重述完整失敗軌跡(兩次做法、錯誤全文、已排除假設) |
| 升到最高 effort 仍失敗 | 取第二意見:另開 agent 獨立解,**不給它自己的推理過程** |
| 第二意見也不收斂 | 停。整理現狀問使用者 |
| 難題解出且同模式要套多處 | 把解法寫成明確步驟,降回低成本 model 批次套用 |
| 任何層級,同一件事 | **最多重試兩輪**,之後只能升級或問使用者,不准第三輪 |

「一輪」= 一次完整的「嘗試 → 驗證失敗」循環。改三行再跑一次測試算一輪,不是三輪。

低成本 model 錯一次即升級,比「兩輪上限」更嚴格,從嚴適用。

**這張表只管能力調整。**「兩輪失敗了接下來該換路、還是該問使用者」屬於 judgment 的職責:
先跑 judgment 判定方向,判定要調整模型能力之後才回到本表。

## 成本與並行

額度數字與來源見 [`references/plan-and-quota.md`](references/plan-and-quota.md)。三件事會改變派工決策:

- **額度是跨 surface 的共用池**:Claude 網頁／桌面／行動版與 Claude Code 共用同一組上限
  (五小時滾動視窗 + 週上限)。省不省額度要看整個池,不是只看當前 session——
  在這裡大量派工,會直接壓縮同一天在 chat 那邊的可用量。額度吃緊時先確認當前用量再決定。
- **並行 subagent 會倍增消耗**。預設**依序派工**,並行僅限彼此獨立且都必要的任務,
  一次最多 2 個。派工前先自問是否落在「何時派工」的三情境內。
- **本 skill 的紀律不會自動套到別的 surface**。Cowork 也吃同一個池,但它官方支援並鼓勵
  平行 sub-agent,方向與這裡的「預設自己做、預設依序」相反;Claude Code 與 Cowork 的
  消耗速率又都明顯高於一般 chat。在 Cowork 跑大任務時額度要另外盯。
- 向下派工(機械掃描交給低成本 model)是真正的省額度手段,而且必須**per-invocation 明寫
  model**——內建唯讀 agent 現在預設繼承主對話模型,不寫就等於用主對話的價格跑掃描。
- **fast mode 不是省額度手段**。它加快輸出、不改變模型品質,而且在訂閱方案上另計費用
  (計費方式見 capabilities 參照)。卡關時關掉 fast mode 的理由是成本,不是品質——
  長時間卡關就是長時間燒錢。

## 選 model 與 effort

| 任務 | 取向 |
|---|---|
| 大範圍機械掃描 / 批次套用(subagent) | 最低成本 model + 低 effort |
| 定義清楚的獨立子任務(subagent) | 中階 model + 中高 effort |
| 主對話日常(實作、重構、review) | 旗艦 model + 預設 effort |
| 模式已定的批次修改、已想清楚只是要打字 | 旗艦 model + 低 effort(趕時間才加 fast mode) |
| 架構、難 bug、第二意見 | 旗艦 model + 最高 effort,**關閉 fast mode** |

三個反模式:**低階 model 配最高 effort**(付推理費給用不上的模型)、
**旗艦 model 配最低 effort**(付旗艦費叫它別想)、
**卡關時開著 fast mode 硬試**(加快輸出不加深推理,又持續燒錢)。

具體別名與級別名稱查 capabilities 參照,並以當前 `/model`、`/effort`、`/fast` 選單為準。

## 驗證交棒(本 skill 不產生驗證判準)

**完成條件與驗收判準屬於 `judgment`,dispatch 不重述、不分叉。**
需要驗收時先跑 judgment,由它決定要不要走 fresh-context 驗證;判定要派工之後,
本 skill 只提供 Claude Code 的執行機制:

- 用 `Agent` tool,`subagent_type` 取**唯讀**的內建探索 agent
  (它跳過 CLAUDE.md 與 git status,天然就是乾淨 context)
- 因為它讀不到 CLAUDE.md,驗收 prompt **必須顯式交付六項輸入**(定義見 judgment 的 verifier
  規則檔——路徑依實際安裝位置而定,派工前查出完整路徑再填入;模板見 templates 參照的模板 6):
  產出物 / 驗收條件 / 適用指示及其**檔案路徑** / revision 或內容 hash /
  允許的驗證方式 / 環境限制。少任一項,verifier 規則要求回報 UNVERIFIABLE
- 需要跑會寫入的驗證(測試、build cache)時:在主對話實跑,或用 `isolation: worktree`
  的隔離 agent。**不得把可寫的通用 agent 當成唯讀用**
- **不要宣稱驗收者必然與主對話同級**:內建探索 agent 已預設繼承主對話模型
  (且可能有上限),再指定 `inherit` 是 no-op,不構成高風險驗收的加強手段
- 驗收 prompt **不含執行者的推理過程**——這是 fresh-context 驗證的前提,不是遺漏
